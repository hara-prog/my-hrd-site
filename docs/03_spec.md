# 要件定義書

> `/spec` を実行すると、Claude が `docs/01_customer.md` を読んでここを埋めます。
> 埋まったら `/build` で実装します。

## 0. 画面の型

- LAYOUT: `stage` 🔮 ── 困りごとの中心が「依頼書の発行漏れ」という**工程の抜け**なので、依頼処理を「未依頼→依頼済み→確定→実施済み」の段階で束ね、止まっている案件が目立つ形が実務に合うと判断した。
- TONE: `indigo` 🔮 ── 企業研修会社は、クライアント企業に対してサービスを提供するBtoB業態のため。
- DENSITY: `roomy` 🔮 ── 月10件前後（1日5件以下）と件数は多くなく、1件あたりの情報量・講師料という金額の重みが大きいため。
- UNIT: `本` 🔮 ── 研修講師業界では「研修を1本入れる」のように数えることが多いと思われるため、「件」より実務の言葉に近い。
  → 確かめ方: 「講師依頼は社内で『1件』『1本』どちらの数え方をしますか？」

## 1. このツールが解くこと

講師依頼1件ごとの情報が1画面で分かり、**依頼書の発行漏れと記入ミスがなくなる。**

## 2. 使う人と、使う場面

- 使う人: 企業研修会社の原社長、および依頼書作成を担当する事務スタッフ
- 🔮 いつ開くか: クライアントとの打ち合わせや電話のあと、情報が入るたびに随時。依頼書を発行する直前にもまとめて確認する。
  → 確かめ方: 「講師依頼の情報を確認・入力するのは、どんなタイミングが多いですか？」
- 開いて最初にしたいこと: まだ「依頼済み」になっていない案件（＝発行漏れの候補）を確認する

## 3. 画面（テンプレートの3画面をそのまま使う）

一覧に、上から順に何が表示されるか。

1. **講師依頼を追加**（講師名・クライアント名・研修日・メモ・ステータスを入れて「追加」）
2. **ステータスごとの一覧**（未依頼／依頼済み／確定／実施済み の4段階で束ねる。各段の件数を見出しに出す）
3. **講師名・クライアント名で検索・絞り込み**できる検索欄（一覧の上部）

## 4. データ項目

| 項目 | 型 | 必須 | 例 |
|---|---|---|---|
| 講師名 | 文字列 | ○ | 佐藤先生 |
| クライアント名 | 文字列 | ○ | 〇〇商事株式会社 |
| 研修日 | 日付 | ○ | 2026-09-10 |
| メモ（研修テーマ・場所・集合時間・講師料など） | 文字列 | - | 新人向けリーダーシップ研修／本社3F会議室／集合12:30／講師料8万円 |
| ステータス | 未依頼 / 依頼済み / 確定 / 実施済み | ○ | 依頼済み |

> 🔮 研修テーマ・場所・集合時間・講師料は本来それぞれ独立して見たい項目だが、テンプレートの5項目制約に収めるため「メモ」に自由記述でまとめた。次回以降、実際の使い方を見て項目分割を検討する。

## 5. 操作（3つまで）

| # | 操作 | 何が起きるか |
|---|---|---|
| 1 | 追加する | 「未依頼」ステータスで一覧の該当する束の末尾に入る |
| 2 | ステータスを進める（未依頼→依頼済み→確定→実施済み） | その依頼が次の段階の束に移動する |
| 3 | 講師名・クライアント名で検索する | 一致する依頼だけに一覧が絞り込まれる |

## 6. やらないこと

- 依頼書・見積書のPDFなど書類の自動発行機能（今回はデータの一覧管理まで）
- 講師本人がログインして自分の予定や空き状況を入力する機能
- クライアント（研修依頼主）向けの提案・マッチング機能
- 研修テーマ・場所・集合時間・講師料を独立した項目に分けること（今回はメモ欄にまとめる）
- 複数拠点・複数人での同時共有（`localStorage` は端末ごとの保存）

## 7. 完成条件

- [ ] 講師依頼を登録すると、一覧に「未依頼」として表示される
- [ ] 講師名またはクライアント名で検索すると、一致する依頼だけに絞り込まれる
- [ ] ステータスを変更すると該当の束に移動し、**リロードしても状態が保持されている**

## 8. 保存方法

`localStorage` に1つのキーで保存する。キー名: `hrd-instructor-requests`
※ 端末ごとの保存です。複数人での共有は第3回で扱います。

## 9. ダミーデータ

初回表示用に3件（すべて架空の講師名・クライアント名・研修内容）。実在の人名・連絡先は使わない。
